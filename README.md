This repository is the Phase 1 foundation for a multi-tenant mobile-shop POS SaaS:
- Laravel API backend
- React + TypeScript + Vite frontend
- Central control database + one isolated database per shop
- Subdomain and custom-domain mapping foundation
- Shop registration and provisioning
- Owner login and role/permission foundations
- English/Urdu language toggle foundation
- Docker Compose for local development

## Important scope note
This is a runnable Phase 1 foundation, not the finished POS product. Inventory, IMEI, billing, repairing, used-phone purchase, accounting, subscriptions billing, offline transaction synchronization, and production-grade custom-domain automation are later phases.

## Requirements
- Docker Desktop (recommended), or PHP 8.2+, Composer, Node.js 20+, MySQL 8+
- Docker Compose v2

## Run with Docker
1. Copy `.env.example` to `.env`.
2. Set secure passwords and `APP_KEY` (generate with `php artisan key:generate` after installing dependencies).
3. Start services:

   ```bash
   docker compose up -d --build
   ```

4. Install backend dependencies and create app key:

   ```bash
   docker compose exec backend composer install
   docker compose exec backend php artisan key:generate
   ```

5. Run central migrations:

   ```bash
   docker compose exec backend php artisan migrate --database=central --path=database/migrations/central --force
   ```

6. Start frontend:

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

Frontend: http://localhost:5173  
Backend API: http://localhost:8000/api/health

## Tenant database provisioning
A tenant database is created when an authorized super-admin registers a shop through `POST /api/super/shops`.
The application database user must have permission to create databases. For production, use a restricted provisioning DB account and a separate runtime DB account.

Tenant DB names are generated by the server (`osm_shop_<random suffix>`); clients cannot choose database names. The central database stores tenant metadata and encrypted DB credentials.

## First super-admin
For local development only, create one with:

```bash
docker compose exec backend php artisan db:seed --class=CentralSuperAdminSeeder
```

Set `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` in `.env` before running. Change the password immediately. Do not expose seeded credentials in production.

## API quick start
- `GET /api/health`
- `POST /api/auth/login` — owner/staff login using tenant slug and credentials
- `GET /api/me` — authenticated user details
- `POST /api/auth/logout`
- `POST /api/super/auth/login` — super-admin login
- `POST /api/super/shops` — super-admin creates/provisions a tenant
- `GET /api/super/shops` — super-admin shop list
- `POST /api/super/shops/{shop}/domains` — attach a domain mapping

The API uses Laravel Sanctum bearer tokens. For local API testing, use the JSON body examples in `docs/API.md`.

## Separate database architecture
- `central`: tenants, domains, super-admin users, provisioning audit events
- tenant DB: users, roles, permissions, shop profile, branches, settings

Tenant connection credentials are encrypted in the central database. This is a foundation; production secrets should be managed with a secrets manager/KMS, not a general-purpose application DB alone.

## Security checklist before production
- Configure HTTPS, secure cookies, rate limiting, mail delivery, backups and restore drills.
- Replace local dev CORS origins.
- Use distinct central, provisioning and tenant-runtime database credentials.
- Enable 2FA for super-admins.
- Add verified email/phone ownership and audited account recovery.
- Do not store plaintext passwords or create hidden developer backdoors.
- Encrypt CNIC files and all sensitive identity documents in a private object store when that module is implemented.
- Configure per-tenant database migrations and scheduled backups.
- Implement custom-domain DNS ownership verification and automated TLS certificates before accepting public custom domains.
